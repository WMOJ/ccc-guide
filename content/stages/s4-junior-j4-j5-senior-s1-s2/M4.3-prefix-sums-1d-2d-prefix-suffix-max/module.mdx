Picture a weather station that logs the rainfall, in millimeters, on every day of a long season. Afterward the program answers questions like "how much rain fell from day i to day j?" A season can run up to 100,000 days. A single run might face 100,000 such questions, each about a different range.

Answering one question is easy: add up every day from i to j. Answering all 100,000 that way is not. Each answer costs up to 100,000 additions, so the batch costs on the order of 100,000 times 100,000, ten billion operations, which is past any judge's time limit even at PyPy's speed. Worse, the ranges overlap, so almost every addition is repeated across several questions.

A <Term id="prefix-sum">prefix sum</Term> array removes that repeated work. It precomputes, once, the running rainfall total from the start of the season up to every day, so that afterward any range's total is one subtraction away.

## Building a prefix sum array

Suppose the season's rainfall is `values = [10, 20, 15, 30, 25]`. The prefix sum array stores the running total up to, but not including, each index: `prefix = [0, 10, 30, 45, 75, 100]`. `prefix[0]` is 0, the total for zero days. `prefix[1]` is `values[0]` alone, 10. `prefix[2]` adds `values[1]`, giving 30. In general, `prefix[i]` is the sum of `values[0]` through `values[i - 1]`.

Starting at `prefix[0] = 0` is what lets the range formula below work even for a range that starts on day 0. There is no `values[-1]` to fall back on, so the array needs an entry for "the total of zero days" to subtract. Building it costs one pass: keep a running total starting at 0 and, after each day, append the new total.

## Answering a range in one subtraction

The rainfall from day i to day j, inclusive, is `prefix[j + 1] - prefix[i]`. `prefix[j + 1]` is the total through day j, and `prefix[i]` is the total through day `i - 1`, everything before the range starts. Subtracting cancels every day before i and leaves exactly the days from i to j.

The `+ 1` is easy to drop. `prefix[j] - prefix[i]` looks similar but leaves out day j, since `prefix[j]` only reaches through day `j - 1`. A single-day range, `i == j`, catches the mistake: the answer should be `values[i]`, and `prefix[i + 1] - prefix[i]` gives it, while `prefix[i] - prefix[i]` gives 0. The "One day" preset above is exactly that check.

Building the array costs one pass over the input, O(N). Each query is then a lookup and a subtraction, O(1), so answering every query costs O(N + Q) instead of O(N times Q). For 100,000 days and 100,000 questions, that is roughly 200,000 operations, not ten billion, and PyPy finishes in a fraction of a second however much the ranges overlap.

## Extending to two dimensions

The same idea reaches a grid. Rain gauges arranged in rows and columns each record a total, and a question now asks for the total inside a rectangle of gauges.

A 2D prefix array stores at `prefix[r][c]` the total of every gauge in the rows before row `r` and the columns before column `c`. That matches the 1D convention, a sum up to but not including each index, so a grid of R rows and C columns gets an (R + 1) by (C + 1) table. Building it needs one extra term to cancel an overlap:

## Prefix and suffix maximums

Prefix sums work because addition has an inverse: subtraction removes the total before day i and leaves the days in between. Maximum has no inverse. Knowing the best value up to day 5 and the best up to day 2 does not tell you the best from day 3 to day 5. That best could be a new value found inside the range, or the very value that was already best up to day 2, sitting outside the range. A prefix max cannot tell those cases apart.

What a prefix max and a suffix max do answer is a range anchored at one end. Picture a leaderboard: `scores`, one entry per submission, in arrival order. `prefix_max[i]` is the best score in `scores[0:i]`, and `suffix_max[i]` is the best in `scores[i:]`. Scanning left to right, `prefix_max[i + 1]` is `max(prefix_max[i], scores[i])`. Scanning right to left, `suffix_max[i]` is `max(suffix_max[i + 1], scores[i])`. Each costs one pass, and each has one more entry than `scores`: `prefix_max[0]` and `suffix_max[n]` are both 0, the best among zero submissions.

## Keeping it fast on PyPy

Every example reads all its input with one `sys.stdin.read().split()` call and walks the list by position, instead of calling `input()` per line or per query. The prefix array is a flat list that gets one append per value, never a re-summed slice per query. Each program collects its answers and writes them once at the end, instead of paying `print()`'s fixed cost inside the query loop. The 2D build binds `prefix[r]` and `prefix[r + 1]` to the local names `prev_row` and `cur_row` once per row, so the inner loop indexes a short row instead of the whole table on every gauge.

## When preprocessing pays off

Preprocessing costs one full pass before the first query lands. If a problem asks only one or two range questions, a direct loop is simpler and just as fast. Reach for prefix sums once the query count, or how much the ranges overlap, lets that one pass over N pay for itself many times. That is the signal M2.9's target-complexity table gives: a faster plan once N or Q reaches the tens of thousands.
