Many problems are really about things connected to other things. People in a social network are connected by friendships. Cities are connected by roads. Pages are connected by links. All of these are graphs: a set of <Term id="vertex">vertices</Term> (the things) and <Term id="edge">edges</Term> (the connections between them).

## Vertices and edges

Number the vertices from 0 to N − 1. Each edge can also carry a weight, such as a distance on a map or a closeness score in a social network. This lesson sticks to unweighted graphs, where every edge counts the same.

## Adjacency list representation

An <Term id="adjacency-list">adjacency list</Term> stores a graph as one list of neighbors per vertex. With vertices numbered 0 to N − 1, that is a list of lists:

```python
adj = [
    [1, 2],
    [0, 2],
    [0, 1, 3],
    [2],
]
```

Vertex 0 connects to 1 and 2, vertex 1 connects to 0 and 2, and so on. If you can travel both ways along an edge, the graph is undirected. Every edge then appears twice: reading an edge between A and B means appending B to A's list and A to B's list. If an edge only lets you travel one direction, the graph is directed, the way a one-way street does, and only one of those two appends happens. The next two sections build both kinds from the same style of input.

An adjacency list uses space proportional to the number of vertices plus the number of edges. It stays small on a sparse graph, one where most vertices only connect to a few others. That covers most graphs you will meet in a contest.

## Iterating over neighbors

Once the graph is built, exploring it means looping over a vertex's list.

```python
adj = [[1, 2], [0, 2], [0, 1, 3], [2]]
current = 0
for neighbor in adj[current]:
    print(f"Vertex {current} connects to {neighbor}")
```

This loop is the piece every graph search is built from. BFS and DFS both start at a vertex, look at every neighbor in its list, and repeat from each new vertex they discover. Everything past this lesson builds on being able to ask "what does this vertex connect to?" quickly, which is exactly what the adjacency list gives you.

## Adjacency matrix versus adjacency list

An <Term id="adjacency-matrix">adjacency matrix</Term> represents the same information as a 2D grid, where `matrix[i][j]` is true exactly when an edge connects `i` and `j`.

```python
matrix = [
    [False, True, True, False],
    [True, False, True, False],
    [True, True, False, True],
    [False, False, True, False],
]
```

A matrix answers "does this edge exist?" instantly. But it always uses space proportional to the square of the vertex count, no matter how many edges actually exist. With 1,000 vertices and only 2,000 edges, the matrix has a million cells for 2,000 real connections. An adjacency list uses space proportional to the edges you actually have. That is why it is the default choice, unless a problem needs fast edge-existence checks on a small, dense graph.

## Recognizing a graph in disguise

The hard part of graph problems is rarely the code, it is noticing that a problem is a graph problem at all. A set of tasks where some depend on others is a graph: vertices are tasks, and an edge points from a dependency to the task waiting on it. Finding a valid order to do them is a search over that graph.

A maze is the same idea with a different name. Each room is a vertex, each passage between rooms is an edge, and finding a way out is a graph search from your starting room.

A flight timetable fits the same shape, but its vertices are not already numbered. `examples/flight_routes.py` reads airport codes instead of vertex numbers. It builds a dictionary from code to index first, then uses that dictionary to fill the same kind of adjacency list as before.

## Getting these details right

Watch for a bug that shows up whenever an edge only gets stored one way. Reading an edge between 0 and 1 and appending just `1` to vertex 0's list loses the fact that 0 is also a neighbor of 1. For an undirected graph, every edge needs both directions stored; for a directed graph, only one.

The input's numbering is another place to check carefully. Some problems number vertices 1 through N instead of 0 through N − 1. Read the first example before you write any code, and if the input starts at 1, subtract 1 from every vertex you read so your 0-indexed adjacency list lines up.

Pick the container to match the vertices. A list of lists, as in every example here, is the right default for vertices numbered 0 to N − 1. When vertex numbers are large and sparse, such as ids in the millions with wide gaps, a dictionary keyed by vertex number skips the vertices that never appear. Vertices might not be numbers at all: names, as with `flight_routes.py`, or grid cells, as with a maze. Either way, map each one to a small index first, then use that index into the same list of lists.
