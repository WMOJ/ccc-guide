A sensor network logs an alert as a `(day, sensor type)` pair, and days are numbered across a billion-day range. Only a few hundred distinct days ever show up in a year of logs, but the day numbers themselves run into the billions. An array with one slot per day cannot be built at that size. Coordinate compression is the fix: renumber the handful of days that actually appear, from 0 upward, and run the rest of the program on those small numbers instead of the originals.

## When expansion is not possible

A list with one slot per day, for a billion-day range, needs a billion slots. Even a bare Python list of pointers costs roughly 8 bytes per slot, so a billion of them is about 8 gigabytes before a single event is recorded. That is well past what a judge grants a program, typically a few hundred megabytes. Filling that list would also take on the order of a billion operations just to initialize, before the input is even read. Neither the memory nor the time is available, and none of it is needed: a season with a billion possible days might only mention a few hundred of them.

## The compression process

Collect every value that appears in the input, sort the unique ones, and give each its position in that sorted order as its new coordinate. Storing that mapping in a dictionary, built once, answers "what is this value's compressed index?" in O(1). Looking a value up with `list.index()` inside a loop instead costs O(n) per lookup, O(n^2) for the whole pass.

## Looking up a value that was never recorded

A query can ask about a value the input never mentioned. "How many recorded days are on or before day 175?" is one such question, when 175 was never logged. `rank` has nothing for a value it never saw. `bisect.bisect_right` answers this instead. Given the sorted list of distinct values, it finds where a query value would sit among them, present or not. That position is exactly the count of values at or before it.

## When you do not need it

A 1,000-by-1,000 grid has a million cells, and a plain array of a million elements is a completely reasonable size on its own; there is no huge range to shrink. Compression also does nothing when a huge range is genuinely used in full. Handed every value from 1 to 1,000,000 with every one of them touched, there is no gap between "distinct values used" and "the full range" for compression to exploit. It earns its keep specifically when the possible range is enormous but the values that actually show up are few. A constraint like "coordinates up to 10^9, but at most 2,000 of them appear" is written that way on purpose, to signal exactly this.

## Getting these details right

Collect every value a later step will need, not just some of them. In an interval problem, that means both the start and the end of every interval; compressing only the starts leaves the ends unmapped. Sort before assigning ranks. Numbering values in the order they first appear, rather than in sorted order, throws away the one property compression exists to preserve. A smaller original value must get a smaller rank. Once the mapping is built, use it consistently. A compressed index and an original value are different things, and treating one as the other undoes the whole point of replacing it.
