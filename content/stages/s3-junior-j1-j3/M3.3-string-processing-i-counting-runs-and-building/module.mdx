Picture a sensor that logs one status letter every second: `a` for normal, `b` for warning, `c` for alert. Over an hour that is 3,600 letters, but most seconds repeat the letter before them, so the log looks like `"aaabbbbccaa..."`, long stretches of the same character. A stretch like that is called a run, and counting runs, then building a new string from what you find, is the core of this lesson.

## Iterating through a string

A string is a sequence, so you can loop through it by index or by character directly:

```python
s = "hello"
for i in range(len(s)):
    print(s[i])
```

The variable `i` walks from 0 to `len(s) - 1`, and `s[i]` reads the character at position `i`. A plain `for char in s:` loop reaches every character too, without an index. Use indices whenever you need to compare a character to a neighbor, since only an index lets you write `s[i + 1]`. Run counting needs them: it keeps asking "does the next character match this one?"

A run is a maximal stretch of one repeated character: in `"aabbcc"` there are three runs, `"aa"`, `"bb"`, and `"cc"`, each of length 2. To measure a run, fix `current_char` at the run's first index, then look ahead one position at a time while the next character still matches:

## How many comparisons does a scan make?

A CCC input string can run past 200,000 characters, so count the work. Suppose the outer loop advanced `i` by 1 each time instead of jumping it forward by `count`, the mistake of forgetting `i += count`. Inside one giant run of length n, that restarts the inner scan from almost the same place at every one of the run's n positions. Each restart checks the rest of the run, so the total is about n²/2 comparisons. At n = 200,000 that is roughly 2 × 10^10, which is a few minutes to half an hour at PyPy's 10^7 to 10^8 simple operations a second, far past any judge's limit. The comparison count below shows the gap on a string of only eight characters.

</Figure>

The restarting plan adds 7, then 6, then 5, and so on down to 28 comparisons in total. The jumping plan finishes the same string in 7, one comparison per character. The "Two runs" preset shows a smaller gap, because each run of 4 is rescanned only within itself. On "All different" the two plans tie at 7, since there is nothing to rescan. `rescan_cost.py` counts both totals with the real loops:

<Code file="examples/rescan_cost.py" showOutput caption="Counting the comparisons of both plans on the same string" />

Jumping `i` to `i + count` is also correct for any string. Every character is compared at most once, either as a character that matches its run or as the one that ends it. Summed over every run, that is at most one comparison per character, so the total stays under n however the runs are distributed. The run's length is exact because its boundary, the first index where the character changes, is exactly what the inner loop's stopping condition detects.

## Making it fast on PyPy

Building `result` by writing `result += str(count) + current_char` inside the loop has a cost worth knowing. In the worst case each `+=` copies every character already in `result` plus the new piece, because strings are immutable and a longer string is a new object. Built that way, a string of length n can cost on the order of n² character copies in total. Appending to a list costs one step per piece, and `"".join` copies the final result once, for about 2n steps altogether. This is a cost model, not a stopwatch, the same kind of counting M2.9 uses for Big-O:

The `+=` line curves upward, the same shape as the `O(n^2)` gap M2.9 shows for a nested loop, and the `join` line stays straight. CPython sometimes optimizes a lone `+=` into an in-place resize. PyPy, the grader's interpreter, has no such guarantee, so rebuilding `result` this way can cost the full n² copies pictured above. Collecting parts in a list and joining once is `O(n)` on every interpreter, which is why `build_transform.py`, `compress_runs.py` and `decode_runs.py` all build their output this way.
