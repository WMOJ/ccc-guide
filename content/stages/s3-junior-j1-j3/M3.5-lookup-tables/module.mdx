A school attendance program needs the number of days in a report's month, for every report in a stack of thousands. A chain of `if`/`elif` statements works: compare the month to 1, then to 2, then to 3, until one matches. For a December report that is twelve comparisons, and the chain repeats them on every report, although each month's answer never changes.

A <Term id="lookup-table">lookup table</Term> stores every answer once, ahead of time, in a list or a dictionary. A query then reaches straight for its entry by index or key, without testing the other possibilities.

## Lists as lookup tables

A list works as a lookup table when the keys are the numbers 0, 1, 2, and so on: the index is the key, and the value stored there is the answer.

```python
days_in_month = [0, 31, 28, 31, 30, 31, 30, 31, 31, 30, 31, 30, 31]
```

Index 0 holds a placeholder, since there is no month 0. Index 1 holds 31, for January, and index 2 holds 28, for February. All twelve entries are filled in before a single query arrives.

A lookup table stores fixed data, but February is not always fixed: a leap year adds a 29th day. Look up the value first, then correct it for the one case that depends on something outside the table. ## Dictionaries as lookup tables

When the keys are not sequential numbers, a dictionary maps any key, such as a string, to a value. The key is what you look up with, and the value is what comes back.

`grades["B"]` reads 80, the value stored under the key `"B"`.

A table does not have to be typed into the code. It can be built from the input a program reads and queried the same way.

This reads pairs of a name and a phone number, stores each pair, then looks up the one name given as the query. Looping over a finished dictionary directly, as in `for name in phone_numbers:`, walks its keys only. Use `.values()` or `.items()` when a loop needs more than the key.

## Building a table safely with `.get()`

Reading a key that was never stored, with `table[key]`, crashes with a `KeyError`. The `.get(key, default)` method returns the stored value if the key exists and the default you give it otherwise, so a query the table never saw does not stop the program.

## Avoiding repeated computation

The saving comes from paying for an answer once and reusing it, which matters most when the same kind of question arrives many times.

Suppose a program needs the day of the year for up to 100,000 dates in one run, each given as a month and a day. Summing every earlier month per query costs up to 11 additions, since December needs January through November added up again. Across 100,000 queries that is up to 1,100,000 additions, and almost all of them repeat a sum an earlier query already worked out. (The sieve in M4.6 is a bigger version of the same idea: one table, built once, over a much larger range.)

## Keeping it fast on PyPy

Build the table once, outside any query loop, the way `days_before` and `vow` both do, so its cost is paid once and not once per query. A list indexed by a small integer is the cheapest lookup PyPy offers: one memory step, no hashing. A dictionary costs a little more because it hashes the key first, so prefer a list whenever the keys are already small whole numbers.

The day-of-year program also collects its answers in a list and writes them once at the end, rather than printing after each query. Keep that habit whenever a table answers many queries in one run.

Reach for a lookup table whenever the same small set of keys is asked about more than once. That covers a fixed rule that never changes, and a value worth precomputing because the program will need it again.
