Picture a digital clock that only shows the hour, 0 to 23. It reads 22 right now. An alarm is set to ring 5 hours from now. Add 22 and 5 and you get 27, but the clock has no hour 27. It counts up to 23, then circles back to 0.

Any count that repeats on a fixed cycle works this way: clock hours, days of the week, seats around a table. That repeating is called <Term id="periodicity">periodicity</Term>, and the length of one cycle is its period. <Term id="modulo">Modulo</Term>, written `%` in Python, wraps a number back into range. `a % b` is the remainder after dividing `a` by `b`. For any `b` above 0, that remainder lands between 0 and `b - 1`, however large or negative `a` is. `27 % 24` is 3, so the alarm rings at 3 o'clock.

## Modulo always lands in range

In Python, `-3 % 24` is 21, not -3. The result is always adjusted into the range 0 to 23, which is what a clock needs: 3 hours before midnight reads 21, not -3.

## A schedule with billions of days

Now a bigger question. A maintenance check happens every `period` days, starting on day `offset`. How many times does it happen within the first `days` days? A senior-level bound might let `days` run past 10^12.

The most direct plan checks every day from 0 up to `days - 1` and counts the ones where the check falls:

```python
period, offset, days = 3, 1, 10
count = 0
for d in range(days):
    if d % period == offset % period:
        count += 1
```

That loop does one comparison per day. PyPy runs on the order of 10^7 to 10^8 simple operations a second. At `days` = 10^12, the loop needs about 10^12 operations, somewhere between ten thousand and a hundred thousand seconds. No judge waits that long, and the answer does not need a day-by-day count at all.

## Counting by cycles, not by days

The checks land on day `offset`, `offset + period`, `offset + 2 * period`, and so on. From day `offset` to the last day of the range, day `days - 1`, there are `days - offset` days. Call that the span. Dividing the span by `period` gives how many full cycles fit inside it, and each full cycle holds exactly one check. The remainder holds one more check if it is not 0, and none if it is.

<Code file="examples/event_count.py" showOutput caption="Counting a periodic event by cycles and a remainder" />

`span // period` is the number of full cycles. `span % period` is what is left over. If that remainder is 0, the last full cycle covers every check up to the end of the range. If it is not 0, one more check fits in the leftover days.

Why is this safe for any span? Cut the days from `offset` to `days - 1` into blocks of `period` consecutive days, the first block starting at `offset`. Every full block starts with exactly one check and holds no other, since the next check is a full period later. A partial block at the end also starts with a check, because it begins exactly `period` days after the previous one. So the count is the number of blocks: `span // period` full ones, plus one more if a partial block is left. That argument does not care how big `days` gets, so the same division and remainder answer it for 9 days or 9 trillion.

## Making it fast on PyPy

`event_count.py` does a fixed, small amount of arithmetic no matter what `days` is, so there is no loop to speed up. It reads all of its input with one `sys.stdin.read().split()` call. A problem that asks for many independent checks keeps that shape: one read, then work through the tokens by position. The total stays proportional to how many checks are asked, not to how large any day count is.

The ring wraps from Sunday back to Monday, the way the calendar wraps from one week into the next. A trillion days takes only four steps, because the hand never walks the weeks. Day -1 lands on Sunday, since `-1 % 7` is 6.

Two slips are worth knowing. The first is the wrong modulus: a 7-day cycle needs `% 7`, a 12-hour clock needs `% 12`, and a 24-hour one needs `% 24`. Using `% 12` on a 24-hour value wraps at the wrong point and gives a plausible-looking wrong answer rather than a crash.

The second appears once several values are each reduced before being combined. `(a % m) + (b % m)` can add up to `2 * m - 2`, outside the range 0 to `m - 1`. Reduce the whole sum once, at the end, with `(a + b) % m`, and it always lands back in range.

Whenever a problem's story repeats on a fixed cycle, modulo turns it into one division and one remainder, whatever the cycle's length and however large the count of steps.
