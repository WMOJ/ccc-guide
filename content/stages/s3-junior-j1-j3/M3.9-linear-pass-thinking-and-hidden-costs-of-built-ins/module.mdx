Suppose you are handed a list of game scores and asked for the lowest and the highest. The obvious plan is two separate scans: one pass to find the minimum, a second pass to find the maximum. That plan reads every score twice. The real danger in this lesson is not that second read by itself. It is a pass that hides inside what looks like a single line of code, buried in a loop that runs once per input.

## Where a built-in hides a second pass

Not every extra pass looks like a second `for` loop. Some hide inside a single call. `numbers.index(value)` walks the list from the start until it finds `value`, so one call costs up to `len(numbers)` comparisons. Calling `index()` inside a loop, once per number you are looking for, turns an innocent-looking line into a nested scan.

The same is true of `value in numbers` when `numbers` is a list: Python scans from the front, the same work `index()` does. A set behaves differently. `value in a_set` costs close to one lookup however large the set has grown, since Python locates the value by its hash instead of by scanning.

## Two pointers on sorted data

Some problems narrow their own search space if the data is sorted first. Given a sorted list and a target sum, one way to find a pair that adds up to it checks, for every number, whether its complement is present. That is an `in` check inside a loop, exactly the hidden cost described above. Sorted order offers a better plan: start one pointer at the first number and another at the last, and let their sum guide which one moves.

<Code file="examples/two_sum_sorted.py" showOutput caption="Finding a pair that sums to a target with two pointers on sorted data" />

Why is it safe to throw a number away forever? Suppose `numbers[left] + numbers[right]` is too small. Every other number still in play is at most `numbers[right]`, `numbers[left]`'s largest possible partner. Pairing `numbers[left]` with anything else only makes the sum smaller still, so `numbers[left]` cannot be part of any answer. Discarding it by moving `left` inward loses no answer. The same argument holds in reverse when the sum is too big: `numbers[right]` cannot pair with anything smaller than its current partner and reach the target, so moving `right` inward is safe. Each move rules out one number for good, so the pointers move toward each other at most `len(numbers)` times before they meet, one pass over the data. (M4.9 covers the two-pointer technique in more depth; this is one example of the shape.)

## Keeping it fast on PyPy

Every example above reads its input with one call, `sys.stdin.read().split()`, rather than calling `input()` once per value. Each one prints its answer once at the end, not inside the loop. The duplicate finder checks membership against a set, not a list. `num in seen` stays fast no matter how large `seen` has grown. A list would make that same check slower with every value added. None of the solving programs above calls `index()`, `count()`, or `pop(0)` inside a loop, each of which rescans or reshuffles the whole list every time it runs. A flat pass with a few running local variables, `min_val`, `max_val`, `left`, `right`, is what PyPy resolves fastest.

## Recognizing the shape

Across all three examples, the pattern repeats. Can the next piece of state come entirely from the current value and what has already been tracked? If yes, one pass suffices, whether the state is a running min and max, a seen set, or a pair of converging pointers. If answering it needs a look back through data already scanned, that look back is where a nested cost hides. It might be a second explicit loop, or a single call that scans internally.

M2.9's table allows an `O(n^2)` plan only up to about `n = 5000`. At `n = 100000`, a list `in` inside a loop does about `n(n-1)/2`, close to `5 * 10^9` comparisons, far more than PyPy finishes in a typical time limit. An `O(n)` plan that keeps the state it needs as it scans does about `10^5` operations on the same input.
