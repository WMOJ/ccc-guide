A small game board arrives as a block of text: a few rows, each the same length, each character either open ground or a mark. Almost any question about it, such as how many cells are marked or what sits beside a given cell, starts the same way. Read the board into a shape Python can index by row and by column, then visit its cells in a fixed order.

That shape is a <Term id="grid">grid</Term>: rows stacked on top of each other, each row holding the same number of columns. In Python, a grid is a list of rows, and each row is itself a sequence, so `grid[row][col]` reaches one cell.

## Reading and storing a grid

Grid input gives the row and column counts first, then the rows, one per line:

```
3 4
..##
#...
....
```

The first line says 3 rows and 4 columns. The house skeleton reads everything with `sys.stdin.read().split()`, which breaks the input into tokens at whitespace. A row like `..##` has no spaces in it, so it stays one token, just as a number does. The counts tell you where the rows end, so slicing `r` tokens off the front rebuilds the grid:

## Indexing rows and columns

The first index of `grid[row][col]` is always the row, counting from the top. The second is the column, counting from the left. Writing `grid[col][row]` still runs, since both are integers, but it reads the wrong cell and gives a wrong answer with no error to point at the mistake.

This visits cells in row-major order: row 0's columns left to right, then row 1's, and so on. A grid with R rows and C columns has R times C cells, and visiting each once costs R times C steps, so the scan is `O(R * C)`. With R and C at most 1000, that is one million steps, which M2.9's target-complexity table puts comfortably inside what a judge finishes in time. Nothing here can be skipped, since any cell might hold a mark, so this brute-force scan is also the whole solution.

## Row and column totals

The same two loops answer a different question once you change what happens inside. A row total fixes `row` and lets `col` run, which is just `sum(grid[row])`. A column total fixes `col` and lets `row` run, so the inner loop goes down the grid instead of across it. In `grid_sum.py` that is the loop over `range(r)` adding `grid[row][col]`.

Watch which index moves. For a row, the highlighted cells share a row index and the column index changes. For a column it is the other way around, and the array beside the grid gets one entry per column, 4 of them instead of 3. The `3 by 4` output above matches: three row sums, then four column sums.

Finding a target works the same way. To locate the one cell holding `'S'`, put `if grid[row][col] == 'S':` inside the loops and save `row` and `col` when it matches. Stopping early saves a little work but leaves the bound at `O(R * C)`.

## Checking a cell's neighbors

A grid question often involves a cell's neighbors: the cells directly above, below, left, and right of it. Writing all four by hand is repetitive and easy to get wrong, so list the four moves as row and column offsets and loop over them.

Adding a pair's `dr` to the current row and `dc` to the current column gives that neighbor's position. A neighbor of a cell on the grid's edge can land outside it: a row below 0, at or past `R`, or the same for columns. Reading `grid[nr][nc]` before checking `0 <= nr < R and 0 <= nc < C` crashes the moment the current cell sits on the border.

## Keeping it fast on PyPy

`sys.stdin.read().split()` reads the whole grid in one call, instead of paying for a separate `input()` call per row. When you only read a character row, leave it as the string `.split()` gave you, the way `count_marks.py` does: converting it to a list costs time and memory for nothing. A problem that asks for several answers over one grid should collect them in a list and print once at the end.

If an answer looks almost right, check three things first. The loop should read `grid[row][col]`, not `grid[col][row]`. Both loops should run over `range(r)` and `range(c)`. And every neighbor lookup should pass the bounds check above.
