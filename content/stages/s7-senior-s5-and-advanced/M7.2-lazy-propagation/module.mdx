A warehouse holds six shelves with `2 4 1 3 5 2` items on them. Events arrive in any order. One says "add 5 items to every shelf from 1 up to, but not including, 5." Another asks for the total on a range of shelves. M7.1's segment tree handles a change to one shelf in $O(\log n)$ steps, but this event changes a whole range.

## Why a range update needs a new idea

Suppose $n$ and the number of events are both up to $2 \cdot 10^5$. Doing a range add as one point update per shelf costs up to $n$ point updates, each $O(\log n)$. Writing each position of a plain array is no better, at $n$ steps per event. So $q$ events cost about $4 \cdot 10^{10}$ steps, far past the budget of roughly $10^8$ simple steps from M2.9.

The insight behind <Term id="lazy-propagation">lazy propagation</Term> is that a range add does not need to reach the leaves right away. The range splits into a few nodes that cover it exactly. These are the same nodes that M7.1's query loop takes. Fix each covering node's own sum now. Then leave a note on it, called a tag: "every leaf below you still owes +5." Compare how few nodes that is with the number of leaves.

## A tag is a debt on a node

Keep a second list, `lazy`, next to `tree`, with the same indexing as in M7.1: leaves at `size + i`, children of `i` at `2 * i` and `2 * i + 1`. The rule has two halves. Every `tree[i]` is the correct sum for its range, counting every update applied at `i` or below, but not tags still waiting at `i`'s ancestors. And `lazy[i]` is an amount each leaf under `i` still owes, which `i`'s children have not received. For a range add, covering a node of length `length` by `v` changes its sum by `v * length`, not by `v`, because every position under it grows.

Two tags on one node combine by adding: a node owing +5 that then receives +3 owes +8. Adds can be applied in any order and still give the same sum, which is why a tag can wait as long as it needs to.

## Pushing before descending

A tag must never be skipped. If a query looked inside a node whose children still owe something, it would read stale numbers. So the code uses the classic push-on-descent rule. Whenever an update or a query is about to visit a node's children, it first pushes that node's tag down. Each child's sum grows by `tag * half` and each child's own tag grows by `tag`. Then the node's tag is cleared.

Why is this enough? Every trip down the tree passes through the ancestors of the node it ends at, and pushes at each one. By the time the walk stands on a node, every ancestor has emptied its tag into the next level, so `tree[i]` and its children are correct. A node that lies entirely inside the range never pushes, because nothing needs to look below it. A node entirely outside is left alone.

## Other updates and the cost

The sum tree scales a tag by the node's length because a sum grows with every position. For range add with range maximum, a tag of +v raises the node's maximum by exactly `v`, so no length appears. Range assignment needs a tag value that means "no tag", such as `None`, because 0 is a legitimate assignment. The composing rule changes as well: a later assignment replaces an earlier one. Choose the tag and its composition first, then the summary's update, and the same recursion applies.

Every update or query visits at most 4 nodes per level and pushes at most once at each partial node, so each costs $O(\log n)$. With $2 \cdot 10^5$ operations that is about $2 \cdot 10^5 \cdot 72 \approx 1.4 \cdot 10^7$ small calls in the worst case, inside the budget. The `lazy` list doubles the memory, which is 524,288 extra entries at $n = 2 \cdot 10^5$.

## Making it fast on PyPy

Keep a tag as one int, so pushing is two additions and a multiply. The `if tag != 0` guard in `push` skips most pushes, since most nodes carry no tag. The nested functions read `tree` and `lazy` from the enclosing scope, which PyPy compiles without extra cost, so there is no need to pass the lists on every call. Read all input once and write all answers in a single call, as the example does.

Reach for lazy propagation when updates and queries both work on ranges. The update must be a tag that composes with another tag and applies to a node's summary in constant time. For point updates only, M7.1's tree is enough.
