A warehouse has 8 shelves holding `3 1 4 1 5 9 2 6` items. Two kinds of messages arrive in any order: one asks for the total stock on shelves 1 up to, but not including, 7, and the other says that shelf 4 now holds 10. With 8 shelves you would add up the slice by hand. With 100,000 shelves and 100,000 messages you need a plan. <Term id="sqrt-decomposition">Sqrt decomposition</Term> cuts the shelves into blocks, stores one total per block, and answers each message in at most about a thousand steps.

## Why the plain plans run out

Adding up the slice for every question costs up to 100,000 steps, so 100,000 questions cost about 10^10 steps, far past the roughly 10^8 that M2.9 derived from a time limit. A prefix array makes each question one subtraction, but a correction rewrites every entry after the shelf. A Fenwick tree (M6.10) takes both messages in about 17 steps each, and M7.1 handles summaries that cannot be subtracted.

Blocks sit between the plain plans and those trees. The code is short, and the summary kept per block can be anything you can rebuild from the block's values. The price is more steps per message, roughly the square root of the length, which is why the lesson ends with the size where that price is lowest.

## Cut the array into blocks

Choose a block size `b`, here the smallest number whose square reaches the length. For 8 shelves, `b` is 3. Shelves 0 to 2 form block 0, shelves 3 to 5 form block 1, and shelves 6 and 7 form a shorter block 2. Shelf `i` lives in block `i // b`. Store one total per block in a list `sums`. The three loops are each simple, and their count is bounded. The first loop runs fewer than `b` times, since `lo` stops at the next multiple of `b`. The second runs at most `n / b` times. The third runs fewer than `b` times, because a block that does not fit has fewer than `b` values left. So a query never costs more than `2 * (b - 1) + n / b` steps.

## When the summary cannot be subtracted

For sums, an update adds a difference. A block maximum has no such shortcut. If the largest value in a block is lowered, the old maximum is gone, and the new one could be any other value in the block. So the update rewrites the value and then recomputes the block's summary from its values, which costs `b` steps.

## Why the block size is about the square root

Small blocks mean many whole blocks per query. Large blocks mean long ragged edges. The total is lowest in between. The figure below takes every possible range over 64 values, runs the three loops with each block size, and records the largest count of additions. The second preset repeats it for 100 values.

The lowest point is at b = 6, with 18 additions, against 64 at b = 1 and 63 at b = 64. Here `2 * (b - 1) + n / b` is smallest near `b = sqrt(n / 2)`, which is 5.7 for 64, and the valley is wide: any `b` from 4 to 10 stays between 18 and 22. The same program prints those numbers.

<Code file="examples/block_cost.py" showOutput caption="The best block size for 64 values by exhaustive count" />

So `sqrt(n)` is a good block size rather than the exact best, and any size of the same order works. For `n = 100,000`, the code's `b` is 317, and a query takes at most about `2 * 316 + 315 = 947` steps. A hundred thousand worst-case queries cost about `10^8` steps. That is at the edge of the budget from M2.9, and on PyPy it comes down to simple loops over two flat lists of ints. For longer arrays or more messages, a tree's log n steps per message leaves more room.

## When to reach for it

Use blocks when range questions and point changes arrive together and a block's summary is cheap to store and rebuild. Write the three-loop query first. If the length is near 10^5, count the steps before you commit.
