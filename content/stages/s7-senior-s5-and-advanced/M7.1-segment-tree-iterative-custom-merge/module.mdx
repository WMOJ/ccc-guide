A shop records its sales for six days: `5 3 8 1 4 7`, numbered from 0. Two kinds of events arrive, mixed together. One asks for the total sales from day 1 up to, but not including, day 5. The other corrects a day: day 3 was really 10, not 1. A <Term id="segment-tree">segment tree</Term> answers both kinds of event in a number of steps that grows with the logarithm of the array's length.

## Why the simple plans run out

Suppose the array length and the number of events are both up to $2 \cdot 10^5$. Adding up a slice for every question costs up to $n$ steps. So $q$ questions cost about $4 \cdot 10^{10}$ steps, far past the budget of roughly $10^8$ simple steps that M2.9 derived from a time limit.

Prefix sums from M4.3 make each question constant time. But a correction to one day changes every prefix sum after it, so each correction costs up to $n$ steps and the total is the same $4 \cdot 10^{10}$. A Fenwick tree (M6.10) handles sums with corrections in $O(\log n)$, but its trick leans on subtraction. Ask for the smallest value in a range, the gcd of a range, or the best run inside a range, and nothing can be subtracted. A segment tree needs only a <Term id="monoid">monoid</Term>: a `merge` of two values that is associative, so `merge(merge(a, b), c)` equals `merge(a, merge(b, c))`, plus an identity value that changes nothing when merged with anything. Sum with identity 0, minimum with a huge number, and gcd with 0 all qualify.

## The tree lives in one list

The idea is a tree of summaries. Each leaf holds one array value, and each node above holds the merge of its two children. The node above leaves 0 and 1 covers positions 0 to 1, its parent covers 0 to 3, and the root covers everything.

Pad the array's length up to a power of two, called `size`, so that every level of the tree is full. The six days become `size = 8`, and the two padding leaves hold the identity, 0 for sums, so they change no answer. Store the tree in a flat list of `2 * size` entries. The leaf for position `i` goes at index `size + i`, the parent of node `i` is `i // 2`, and its children are `2 * i` and `2 * i + 1`. Index 0 is never used. The reason this is correct is an invariant. At every level, the nodes from `lo` up to, but not including, `hi` cover exactly the part of the range not yet taken. If `lo` is even, it and its right neighbor are both inside the range and share one parent, so moving up loses nothing. If `lo` is odd, it is a right child, and its parent would reach one leaf to the left of the range. So `lo` is taken alone and skipped over, which makes it even. The same argument holds mirrored for `hi`. Each level takes at most two nodes, and there are log2(size) levels.

For $n = 2 \cdot 10^5$ the size is 262,144, or $2^{18}$, so a query takes at most 36 nodes. All the queries together cost about $7 \cdot 10^6$ merges, well inside the budget. The second preset asks for the whole array and takes two nodes, 6 and 2, rather than the root, because the root also covers the padding. The third asks for one day and takes a single leaf.

The loop keeps `left_part` and `right_part` apart, and merges the right side as `merge(tree[hi], right_part)`, with the new node on the left. Nodes taken from the left edge arrive left to right, but nodes taken from the right edge arrive right to left. Two accumulators keep the final order correct. For sums the order does not matter, but for the merge later in this lesson it does.

## A custom merge: the best run inside a range

Because the tree only needs an associative `merge`, a node can hold more than one number. Take the question "what is the largest sum of a contiguous run inside this range?" One number per node is not enough. The best run inside a parent might cross the boundary between its children. So each node stores four numbers: the `total` of its range, its best `prefix` (a run starting at its left end), its best `suffix`, and the best run `inside`.

Merging a left node `a` and a right node `b` gives `total = a.total + b.total`, `prefix = max(a.prefix, a.total + b.prefix)`, the mirror for `suffix`, and `inside = max(a.inside, b.inside, a.suffix + b.prefix)`. The last term is the run that crosses the boundary. Try the merge step by step below, using queries on the sample array.

On `-2 1 -3 4 -1 2 1 -5 4` the best run is `4 -1 2 1`, which sums to 6. After position 7 changes from `-5` to `0`, the run extends to `4 -1 2 1 0 4` and the answer is 10. Swapping the arguments of either merge call in the query loop would quietly break this result, because prefix and suffix depend on which side a node sits on. Rounding can break associativity for floating-point values, so prefer integers.

## Keeping it fast on PyPy

Keep the tree in one flat list of ints. The `merge` function costs little, because PyPy compiles a small call in a hot loop down to the operation inside it. The tuple version allocates one small tuple per merge, which is fine for a few million merges. When the merge is a single comparison, as with minimum, drop the wrapper function, call the built-in `min` directly, and keep the running answer in one local variable:

Reach for a segment tree when updates and range questions arrive mixed and the question cannot be undone by subtraction, such as minimum, maximum, gcd, or a bundle of numbers. For sums alone a Fenwick tree is shorter. For updates that change a whole range at once, the next lesson adds one idea to this same layout.
