A print shop has four jobs queued on one machine. Each job takes some minutes, and each has a weight: how much it costs per minute while the customer waits. A job's cost is its weight times the minute it finishes, and you want the order with the smallest total cost. Four jobs have only 24 orders, but 20 jobs have about 2.4 * 10^18, far past the 10^8 or so operations a solution can afford (M2.9).

M4.2 already gave a rule for one case: with every weight equal, run the shortest job first. That rule ignores weights, so it needs a new key. Finding the key and proving it correct takes an <Term id="exchange-argument">exchange argument</Term>. Take any schedule and swap two neighbors that the <Term id="greedy-algorithm">greedy algorithm</Term> would have placed the other way. Then show the cost does not rise.

</Figure>

Jobs outside the pair finish at the same minute either way, so only `x` and `y` change. The start offset `s`, the minutes `P` takes, delays both orders by `s` and cancels. What is left: with `x` first, `y` waits `t_x` minutes, costing `w_y * t_x`. With `y` first, `x` waits `t_y` minutes, costing `w_x * t_y`. In the figure that is 4 x 3 = 12 against 1 x 2 = 2.

So `x` belongs first exactly when `t_x * w_y <= t_y * w_x`. Dividing both sides by `w_x * w_y` turns this into `t_x / w_x <= t_y / w_y`: the job with the smaller time per unit of weight goes first. Comparing by cross-multiplication keeps everything in integers, so nothing rounds.

## From one swap to the whole schedule

The pair argument proves more than it seems to. Start from any order. If some neighboring pair is out of `t / w` order, swap it: the cost does not rise. Each swap removes one out-of-order pair and creates none. After at most N(N - 1) / 2 swaps no neighboring pair is out of order, and the list is sorted by `t / w`. Tied jobs can sit in either order, because swapping them changes nothing. Every schedule can be carried to the sorted one without ever paying more, so the sorted schedule costs at most as much as any other. That is the exchange argument. The step-through below runs it.

## Deadlines and the worst lateness

Change the goal. Each job has a time `t` and a deadline `d`. A job's lateness is its finish minute minus its deadline, negative when it finishes early, and the goal is to minimize the largest lateness. Take `x` right before `y` with `d_x > d_y`, out of deadline order. Before the swap, `y` finishes at minute `f` and its lateness is `f - d_y`. After it, `y` finishes earlier, so it is less late, and `x` finishes at `f`, with a lateness of `f - d_x`, which is smaller than `f - d_y` because `d_x` is larger. The pair's worst lateness does not rise, so earliest deadline first is optimal. The figure swaps pairs until that order appears.

## Choosing meetings that do not overlap

Now pick as many meetings as possible, no two overlapping. Sorting by end time and taking each meeting that starts at or after the last chosen end is optimal. The exchange: if an optimal choice starts with some other meeting, swap that one for the earliest-ending meeting. The new meeting ends no later, so it overlaps nothing the rest of the choice contains, and the count stays. Repeat from the next meeting on.

## When the swap fails

An exchange argument either works or shows you where it breaks. Give each meeting a value and ask for the most total value, and the swap above fails. Replacing one meeting with the earliest-ending one can throw away a valuable meeting. That version needs dynamic programming. When you cannot build a swap that leaves the cost no higher, the greedy rule is a guess. Test it against brute force on small inputs before trusting it.

Reach for an exchange argument when a problem asks for a best order or a best selection and a sorting key suggests itself. Write the cost of two neighbors in both orders, subtract, and see whether the difference depends only on the pair. If it does, the key falls out of the algebra.
