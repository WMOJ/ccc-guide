A token starts on square 0 of a strip. Each turn a fair coin decides the move: heads moves it one square, tails moves it two. The game ends as soon as the token reaches square 3 or goes past it. How many turns does a game last, on average? That average is the <Term id="expected-value">expected value</Term> of the number of turns: every way the game can go, weighted by its chance.

## Expected value from the definition

Every sequence of moves is a path, and its chance is the product of the chances of its moves. A path that lasts `t` turns with chance `c` contributes `c * t` to the expected value, and the expected value is the sum of these contributions over all paths. The stack holds `(square, chance, turns)` for each path still being played. A path that reaches the end adds `chance * turns` to `expected`. The count of paths is the trouble: each extra square multiplies it by about 1.6. A strip of 30 squares has 2,178,309 paths, and a strip of 40 has 267,914,296. With N up to 10^5, the size M2.9 pairs with an O(N) plan, enumerating paths is out of the question.

## Work backward from the end

Look at what the future of a game depends on. Once the token sits on square 2, the rest of the game is the same however it got there. So give each square its own answer: `e[i]` is the expected number of turns still to play from square `i`. At or past the end nothing is left, so `e` is 0 there. Anywhere else one turn is played, and then the token is on square `i + 1` with chance `p` or on square `i + 2` with chance `q = 1 - p`:

`e[i] = 1 + p * e[i + 1] + q * e[i + 2]`

This is correct because it is the definition again, weighted over only the first move. After that move the game restarts from a new square, and its expected value is that square's `e`. ## Add expected values, even for dependent pieces

A second route needs no recurrence for `e`. Count turns by where they end. Each turn lands the token on one square. Squares 1 and 2 are landed on at most once each, and the final turn lands at or past the end. So the number of turns is 1 plus the number of squares among 1 and 2 that the token lands on.

<Term id="linearity-of-expectation">Linearity of expectation</Term> says the expected value of a sum is the sum of the expected values. A square counts 1 if the token lands on it and 0 if not, so its expected value is just the chance of landing there. That holds although the pieces depend on each other: landing on square 2 is more likely when square 1 was landed on. Nothing has to be known about how they interact. ## Printing the answer

The chances here are sums of powers of two, so the floats are exact. A chance like 0.1 is not, and each operation adds a relative error near 10^-16. Over a million squares the total error stays far below a typical tolerance. Keep full precision until the last step, then format once, as in `f"{expected:.4f}"`, with as many digits as the statement asks for. When a statement wants the answer as an exact fraction modulo a prime, M7.6 shows the tool for the division. On PyPy, one flat list of floats and one loop are enough: a million squares is a million iterations.

Reach for this when a question asks for an average or a chance over random choices. If the situation after a move depends only on where you are, define a value per state and fill it from the end. If the target is a count, try linearity first.
