Suppose you have written the running-minimum method from the subtask lesson: the largest sum over any run of consecutive numbers, in one pass. It passes the sample. You cannot see the judge's tests, so you cannot tell whether it fails on some input you never thought of. What you can do is write the slow method you would trust on sight, feed both methods the same small random inputs, and wait for them to disagree. That loop is a <Term id="stress-test">stress test</Term>. It needs a trusted <Term id="brute-force">brute force</Term>, the fast function under test, a generator of small random inputs, and a comparison that stops at the first difference.

## The parts in one file

Everything lives in one file, so there is no second program to launch.

`brute` tries every start `i` and every end `j`, sums the slice, and keeps the largest. It reads straight from the problem, so you can check it by eye. `fast` is the prefix-sum method from the subtask lesson, with a running minimum in `low`. It has one planted slip: `low` starts at `prefix[1]`. That is an easy mistake to make when `prefix[0]` looks like a formality.

`new_case` makes one input: a length from 1 to 3 and values from -3 to 3. Both ranges are small on purpose. Short arrays keep a failing input readable, and the brute force finishes instantly. A narrow value range makes zeros, ties and negative numbers turn up within a few trials, where values up to a billion would almost never hit them. The seed comes from standard input and goes to `random.seed`, so the same seed always produces the same trials and a failure can be rerun exactly.

## Shrinking the failing input

## Finding the mistake

Now trace the buggy function on that small input. `prefix` is the running-total array from the prefix sums lesson. The marker `low` sits on the smallest entry so far, and `end` is the entry being tried. Try all three presets.

<Figure caption="The buggy function on the shrunk input: low never offers prefix[0]">
  <StepThrough frames="visuals/diverge.frames.json" preset="positive" />
</Figure>

On `[4, 1]`, `low` starts at `prefix[1]`, which is 4. The first candidate is `prefix[1] - prefix[1]`, which is 0, an empty range. The second is `5 - 4 = 1`. The whole array, `prefix[2] - prefix[0]`, is never tried, so the function returns 4 while the brute force finds 5. The negative preset shows the other symptom, which has the same cause: for `[-4]` the empty range counts as 0, and 0 beats the true answer. The fix is one line, `low = prefix[0]`.

## What a pass does and does not show

A pass means the fast function matched the brute force on every trial you generated. It does not prove the function correct. If the brute force is wrong, both can share the mistake, which is why the brute force should be the plainest code you can write. If the generator never produces some shape, such as a huge value or a long array, that shape goes untested. Change the seed, widen the ranges, and rerun. Each seed is a different run of 1000 trials, and a thousand trials on arrays this small take a fraction of a second. Keep the stress file out of your contest submission: it is a tool for your own machine.

Reach for a stress test when you have a fast method you cannot verify and a slow method you can, and the problem's inputs can be made small.
