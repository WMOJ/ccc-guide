A bakery logs its profit or loss for each of N days. Given those N numbers, find the largest total over any run of consecutive days, where a run has at least one day. The statement ends with a table of <Term id="subtask">subtasks</Term>, as statements do:

> Subtask 1: N ≤ 300.
> Subtask 2: N ≤ 4000.
> Subtask 3: N ≤ 1,000,000.

Each subtask is a batch of tests with its own bound on N. The bounds are facts about the tests, and each one tells you how much work a plan can afford. The complexity module pairs each bound with the growth a plan can afford: N up to about 500 allows `O(N^3)`, N up to 5000 allows `O(N^2)`, and a million needs `O(N)` or `O(N log N)`. This lesson builds one program per subtask for this problem and checks each against its bound. The judge keeps your best result across submissions, so a program for Subtask 1 is worth sending before you have anything faster.

For N days there are `N(N + 1) / 2` pairs, and summing a slice adds up to N numbers, so the plan does about `N^3 / 6` additions. That is cubic, and the complexity table allows it at N ≤ 300.

## Subtask 2: stop re-adding

The slice `values[i:j + 1]` is summed again from scratch for every `j`, although it differs from the previous slice by one number. Keeping a running total for each start removes that repeated work:

The output is the same, and each pair now costs one addition, so the plan does `N(N + 1) / 2` of them. That is quadratic, and the table allows it at N ≤ 5000.

## Subtask 3: prefix sums with a running minimum

A run from `i` to `j` sums to `prefix[j + 1] - prefix[i]`, where `prefix` is the <Term id="prefix-sum">prefix sum</Term> array. Fix the end `j`. Then `prefix[j + 1]` is fixed, and the run is largest when `prefix[i]` is smallest among `prefix[0]` through `prefix[j]`. So instead of trying every start, keep one number, `low`: the smallest prefix entry seen so far. The best run ending at `j` is `prefix[j + 1] - low`, and the answer is the largest of those over all `j`.

<Code file="examples/prefix_min.py" lines="4-18" showOutput caption="One pass: the best run ending at each day, using the smallest earlier prefix" />

At `j = 4`, `low` is `-1` from `prefix[2]`, so the candidate is `4 - (-1) = 5`, the run `values[2:5]` the brute force found. The gains preset shows why `low` starts at `prefix[0]`, which is 0: there the best run starts at `values[0]`, and only `prefix[0]` can be subtracted for it. In the dip preset, `low` drops from 0 to -1 at `j = 1`, and `best` rises from 2 to 4 at `j = 2`. In the losses preset `best` ends at -1. Each day costs one addition to build `prefix` and a few more operations in the loop, so the work grows in step with N. That is linear, and it fits a million days. `best` starts at `values[0]`, the run of one day, so a list of losses still reports its largest single value. The `prefix` list then holds a million and one integers, roughly eight megabytes on PyPy by the memory rule of thumb, which fits.
