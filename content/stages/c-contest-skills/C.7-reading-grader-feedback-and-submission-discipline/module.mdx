A verdict belongs to one test, so read the whole list before you touch the code. A subtask stops at its first failing test, so the first failure is the one to chase. DMOJ reports an uncaught Python error as `IR` rather than `RTE`, and the same steps apply.

## A time limit: count the work

A `TLE` says nothing about correctness. The program may print the right answer, just too late, so the first check is arithmetic. A loop inside a loop over `2 * 10^5` values is about `2 * 10^10` steps, far more than PyPy's `10^7` to `10^8` simple operations per second allows.

The program below asks whether any value appears twice, and counts the work two ways. `slow_checks` compares each value with every value before it. `fast_checks` looks each value up in a set. The list has no repeated value, which is the worst case for both.

Each tenfold step in n multiplies the list scan's count by about 100, and at n = 20,000 it passes `10^8`, while the set's count equals n. Now switch to the second preset. When two equal values sit at the front, the list scan stops after one check at every size. A judge test like that passes instantly, so the same program can earn `AC` on some tests and `TLE` on others. Time the worst case you can build: the largest n, with no early exit.

If the counts look small and the run is still slow, check how the program reads input. Reading all of standard input once with `sys.stdin.read()` usually costs less than calling `input()` once per line.

## A memory limit: count what you store

An `MLE` means the program holds more than the limit allows, so count what it stores. A table of N rows with N values each holds `N^2` numbers. At N = 5,000 that is 25 million numbers, about 200 MB at the 8 bytes per integer the complexity module gives. Ask whether you need the whole table at once or only the row you are working on.

## Submitting with discipline

Before you resubmit, reproduce the failure locally. Run the small input you suspect and watch it fail for the reason you think. A fix you cannot test on your own machine is a guess.

Then change one thing. If you change two and the verdict improves, you do not know which change helped. If it gets worse, you do not know which one hurt. A change of verdict is still information: a `WA` that becomes `TLE` means the wrong-answer tests now pass and a new problem has appeared.

Keep a short log: what you changed and what the verdict was. After two submissions that taught you nothing new, stop submitting. Reread the statement and the sample, and build a test that none of your earlier tests covered.

Reach for this routine on any verdict that is not `AC`: name the verdict's likely cause, reproduce it on a small input, change one thing, and submit again.
