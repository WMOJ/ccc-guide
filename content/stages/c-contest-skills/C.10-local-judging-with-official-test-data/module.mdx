Suppose your solution passes the samples in the problem statement and your own edge cases. You still do not know how it does on the data the grader actually used. For a past CCC problem you can find out: CEMC publishes the exact input and output files it judged with, once the contest is over. The module on testing covers building your own tests. This lesson covers running a solution against those official ones.

## What the official test data is

[CEMC's past-contests page](https://cemc.uwaterloo.ca/resources/past-contests) makes the official inputs and expected outputs available alongside the problem statements. Every input the grader used is there, and next to it the exact output the grader expected, grouped by problem. It is the real data, for a problem whose contest window has closed.

Keep one problem's files together in a folder named after the problem, with each input file next to its matching output file. The script later in this lesson relies on that pairing. Sorting the files once, when they arrive, saves you from working out which output belongs to which input on every rerun.

## What this data checks that a sample cannot

A hand-made test and an edge-case test both rely on you noticing which cases matter, then working out the correct answer yourself. The official data removes both steps. It covers the cases the problem's author intended, and its expected outputs are correct by definition, since they are what the grader used. Running every file mirrors what the grader does when it checks each subtask, and it is the closest offline equivalent for a problem you can no longer submit.

A mismatch also tells you which case fails. If every small file matches but a large one does not, suspect a bound your solution handles only up to a point. If one file fails while larger ones pass, suspect a specific case your plan overlooked.

The first mismatching line is enough to fail the file: once one line differs, the file's verdict is "differs", whether the rest agrees or not. Some real judges ignore trailing whitespace, so a file that fails this strict local check may still be accepted. An exact check is still what you want when hunting for a difference, because it never hides one.

## Timing is only a hint here too

The module on complexity analysis explains why a run on your own machine is not proof a plan is fast enough. Running against official data changes nothing about that. Your machine is not the grader's machine, and plain CPython is often ten to fifty times slower than PyPy, the same estimate that module gives. A local timing on the larger files gives a rough sense of whether the solution is in the right range. Matching every official output exactly is a strong check of correctness. Treat any timing you notice along the way as a hint, never as the grader's own answer.
