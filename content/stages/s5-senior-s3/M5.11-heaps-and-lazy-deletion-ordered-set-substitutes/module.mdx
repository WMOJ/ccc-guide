Imagine a job queue where a waiting job can grow more urgent while it waits. You always want the most urgent job the queue knows about, even as priorities keep changing underneath it. A <Term id="heap">heap</Term> is built for exactly this: a list, kept in a special order, that returns the smallest (or largest) item in logarithmic time.

Scanning the whole queue for the most urgent job costs $O(n)$ per query. A contest version can push both the job count and the query count to $2 \cdot 10^5$, so scanning every query costs $O(n^2)$ in the worst case, around $4 \cdot 10^{10}$ steps. M2.9's bound-to-complexity reasoning rules that out: a budget near $10^8$ steps needs a per-query cost that does not grow with $n$. A heap gives that, answering each query in $O(\log n)$ however many times a priority changes.

## Heaps in Python

Python's `heapq` module turns a plain list into a min-heap: index 0 always holds the smallest item. Push adds a new item at the end, then moves it up past any bigger parent. Pop removes index 0, moves the last item into its place, then sifts that item down past any smaller child. Both operations cost $O(\log n)$, the tree's height.

## Lazy deletion: skip stale entries instead of updating them

Suppose a job's priority improves while it is already in the heap. `heapq` has no fast way to update a buried entry, and even finding it means scanning the whole list. Push a new entry with the better priority instead and leave the old one where it sits, a trade called <Term id="lazy-deletion">lazy deletion</Term>.

To tell the two apart later, keep a list of each item's current best priority, one slot per item. When an entry pops, compare its priority to that slot: a match means it is current, and a mismatch means a later push already replaced it, so skip it.

## A multiset with pending removals

A <Term id="multiset">multiset</Term> lets the same value appear more than once, and needs to answer "what is the current maximum" as items are added and removed. A heap gives fast access to the maximum, but removing "the value 9" is the out-of-date-entry problem again: you cannot search the list for it quickly.

Marking a *value* as removed does not work if a duplicate is still present: a set of removed values would throw away every future 9, not just the one that left. A pending-count dict, keyed by value, fixes this instead. Removing a value increases its pending count by one. A query then pops entries off the top, discarding each one whose value still has a positive pending count, until it finds an entry with nothing pending against it.

Each removal consumes exactly one stale heap entry this way, however many equal values are mixed together.

## Sliding-window minimum with a heap

A sliding window of fixed size $k$ moves one step at a time: it gains the element on the right and loses the element on the left. Rescanning all $k$ elements for the minimum on every step costs $O(nk)$ over the whole array. A heap of `(value, index)` pairs answers each step in $O(\log n)$ instead. Push the new index, then before reading the minimum, pop any entries whose index has already left the window.

## Why lazy deletion is worth the cost

Lazy deletion trades a search for a skip. Updating an entry in place means an $O(n)$ scan of the heap's list to find it, then fixing the heap property around it. Pushing a replacement instead costs one comparison per skip, since a stale entry is only ever compared, never searched for.

The total cost still stays bounded, because every entry pops at most once, used or skipped. If a program pushes $M$ entries in total and $K$ turn out stale, the total work is $O((M + K) \log M)$, with $K \le M$. In practice $K$ stays far smaller than $M$: a job's priority improves once or twice, not thousands of times.

## Making it fast on PyPy

Senior problems in this shape often push both the item count and the update count to around $2 \cdot 10^5$. Read the whole input once with `sys.stdin.read().split()` and take tokens by position, as every example above does; calling `input()` that many times costs far more. Number items as plain integers when you can, since PyPy hashes small integers faster than strings. Keep the heap itself a single flat list, never a list of custom objects, since `heapq` works directly on plain lists. Above all, resist the urge to search the heap to fix an entry in place: reintroducing that cost in a hot loop erases the whole benefit of using a heap.

Reach for a heap with lazy deletion whenever a problem asks for a repeated minimum or maximum over a changing collection. Values improve, items are removed, or a window slides across an array; the pattern stays the same.
