Five friends, numbered 0 to 4, each buy one gift. Everyone receives exactly one gift, and nobody may buy for themselves. Write `gift[i]` for the friend that friend `i` buys for. You need a list in which no `gift[i]` equals `i`.

One way to find such a list is to shuffle and look. Put the friends in a random order, check that nobody landed on their own number, and start over if someone did. An algorithm that makes random choices like this is a <Term id="randomized-algorithm">randomized algorithm</Term>.

## Shuffle, check, repeat

With 12 friends there are 479,001,600 lists, so trying them all in order is out of the question, and for 200,000 friends it is hopeless. Random shuffling works because a valid list is not rare. Of the 120 lists for five friends, 44 are valid, about 37 in 100, and that share stays near 37 in 100 however many friends there are.

The shuffle is the standard one. Walk position `i` from the last position down to 1, pick a random position `j` from 0 through `i`, and swap `gift[i]` with `gift[j]`. There are `n` choices for the first swap, `n - 1` for the next, and so on down to 2, so `n!` equally likely sequences of choices, and each one produces a different list. Every list is equally likely.

## How many tries are enough

If each try succeeds with probability p, then k tries all fail with probability (1 - p) to the power k. Looping until success has no failure probability at all, only a running time: about 1 / p tries, here under three. The arithmetic matters when you run a fixed number of trials, because you cannot afford to loop forever or because the program cannot check a guess. Then you choose k so that (1 - p)^k falls below a target, for example one in a million.

## Random pivots

Take eight numbers and ask for the fourth smallest. Sorting answers it in `n log n` steps, and for one query `sorted(values)[3]` is usually the right choice. <Term id="quickselect">Quickselect</Term> answers it in about `n` steps on average and is the clearest place to see what a random choice buys.

Pick a number from the list as the pivot. Split the list into the numbers smaller than the pivot, the numbers equal to it, and the larger ones. Counting tells you which group holds the answer. If the wanted position is below the size of the smaller group, the answer is in it. If it falls inside the equal group, the answer is the pivot itself. Otherwise it is in the larger group, at a position reduced by the two groups you passed. Keep that group and repeat.

Why bother with randomness? Suppose the pivot is always the first element. On sorted input that element is the smallest, so each round removes only the pivot, and finding the middle value compares about `n + (n - 1) + ...` times, roughly three eighths of `n` squared. For `n` = 200,000 that is about $1.5 \cdot 10^{10}$ comparisons, far past a budget of roughly $10^8$ steps. A random pivot has no bad input. It lands in the middle half of the sorted candidates with probability one half, and then at most three quarters remain. On average, two rounds shrink the list to three quarters. Adding up $2n(1 + 3/4 + (3/4)^2 + \dots)$ gives at most $8n$ comparisons on average, whatever the order of the input.

## Seeds make a failure repeatable

A randomized program that fails once is hard to debug if it never fails the same way twice. Calling `random.seed(value)` puts the generator in a known state, and everything drawn afterward repeats exactly. This page fixes seeds so each example prints the output shown, and the examples read the seed from their input for that reason. In your own solution, print the seed while you test, and reuse it to replay a failing run. If you never call `random.seed`, Python seeds itself from the operating system, so each submission gets a fresh draw. With a fixed seed, every judge run repeats exactly. Either choice is sound when the failure probability per test is tiny, but a fixed seed that fails a test fails it every time.

## Is it fast enough

Size the plan the way you size any other: the number of trials times the cost of one trial must fit in about $10^8$ simple steps. A try over 200,000 friends is a shuffle plus a check, a small multiple of 200,000 steps, so 30 tries is on the order of $6 \cdot 10^6$ steps and fine. A success probability of 0.01 would need 1,375 tries for one in a million, about $2.75 \cdot 10^8$ steps, which is more than one run can afford. Either the trial must get cheaper or the odds better.

On PyPy, every `random.randrange` or `random.randint` call is a function call, so a loop that draws ten million times spends much of its time there. Quickselect draws once per round, and `random.shuffle` runs its swap loop inside the library like any other loop. Quickselect's list comprehensions copy lists that shrink each round, so the copying adds up to about the comparison counts shown above. Flat lists of integers keep each trial cheap.

Reach for randomness when a check is cheap and a good outcome is common enough to put a number on. Then pick the number of trials so the failure probability is negligible.
