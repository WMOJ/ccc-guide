Picture a sorted class list and a question: how many students scored exactly 85? Scanning every name to count them costs one comparison per student. A sorted list holds a shortcut: compare the middle name, decide which half can still contain 85, and throw the other half away. Repeat on the half that is left. Each comparison halves the work, so `N` names cost about $\log_2 N$ comparisons instead of `N`. This is <Term id="binary-search">binary search</Term>, and it applies to more than positions in an array.

## Using bisect_left and bisect_right

Python's `bisect` module already implements this halving over a sorted list. `bisect_left(arr, x)` returns the leftmost index where `x` could be inserted without breaking the order. If `x` already appears, that index is its first occurrence. `bisect_right(arr, x)` returns the index just past the last occurrence instead. Subtracting the two gives the count of `x` in the array, in O(log N), with no explicit loop of your own.

## Binary search on the answer

A different family of problems hands you no array at all. Instead, you are asked for the smallest or largest number satisfying some condition, and checking one candidate costs real work of its own. Suppose that condition is monotone: once a value works, every larger value works too, or every smaller one does. Then the same halving idea searches the values directly, never touching an array.

Suppose a delivery truck makes several trips, in a fixed order, and cannot reorder the packages waiting for it. What is the smallest capacity that still gets every package delivered in that many trips? Checking one candidate capacity `cap` is a greedy pass: start a new trip whenever adding the next package would exceed `cap`, and count the trips used. If `cap` needs three trips, any larger capacity needs three or fewer, since a bigger truck only combines loads, never splits them. The condition "needs at most the allowed number of trips" is monotone in `cap`, so binary search applies to the capacity itself.

With `n` up to $2 \cdot 10^5$ packages and capacities up to the sum of all weights, checking every candidate capacity one by one costs a full greedy pass per candidate. Near the largest weights that is up to `n` candidates, each an O(n) pass. That is an O(n^2) plan, reaching $4 \cdot 10^{10}$ operations at the bound, far past what a judge finishes in time. Binary search checks only about $\log_2$(total weight) candidates, each still an O(n) pass, for O(n log(total weight)) overall.

## Why it works, and how it breaks

The loop keeps an invariant: every value below `lo` has been shown infeasible, and every value at or above `hi` is either feasible or has not been ruled out. The true answer is always somewhere in `[lo, hi]`. Checking `mid` shrinks that range by roughly half either way, so after about $\log_2(hi - lo)$ checks, `lo` and `hi` meet on the answer. This reasoning depends entirely on monotonicity. If a candidate could fail right after a smaller one succeeded, the split point this loop assumes would not exist. The search could then converge on a value that only looks right because the loop stopped there. Confirm the monotonicity on paper, with a couple of concrete numbers, before writing the search.

Keeping that invariant true depends on getting both updates right, and one wrong update is the most common bug in this template. The loop condition must be `lo < hi`, not `lo <= hi`: once they meet, there is nothing left to narrow. The update on success must be `hi = mid`, since `mid` itself might be the answer and moving `hi` past it would discard a value the invariant still needs to hold onto. On these three packages weighing 5, 4, and 2 with at most two trips allowed, this update discards capacity 6, the true answer, the moment it is checked. It treats a feasible `mid` the same way the correct code treats an infeasible one. The search still terminates, printing 5, but 5 fails its own check: `trips_for` on these packages needs three trips at capacity 5, not two. A broken update does not always announce itself with an infinite loop. It can just as easily hand back a wrong number that looks plausible until you check it. Python has no integer overflow to worry about here, unlike the classic `mid = (lo + hi) // 2` trap in fixed-width languages, but that only removes one hazard, not the two update rules above.

## When to reach for which tool

If the data is already sorted and you want a position or a count, call `bisect_left` or `bisect_right`. They are part of the standard library, implemented in C even under PyPy, so there is no reason to hand-write this loop for that case. If instead you are hunting for a number that satisfies a monotone condition, and testing one candidate is its own small computation, write that check as a function. Then binary search on the answer, using that function. Keep `lo`, `hi`, and the candidate function as local variables. Read all input at once, the way `capacity_search.py` does, so the cost stays in the check itself rather than in Python's own overhead. Both tools are the same halving idea: one searches positions in an array you already have, the other searches values you have not enumerated at all.
