Add up `n // d` for every `d` from 1 to 8. The terms are 8, 4, 2, 2, 1, 1, 1, 1, and they sum to 20. Look at how they repeat: the two 2s sit side by side, and so do the four 1s. As `d` grows, `n // d` only falls, and it falls in steps, so equal values always come in runs. A run of consecutive `d` with the same quotient is a block, and one multiplication can add up a whole block at once.

That matters once `n` is large. Suppose a problem asks for this sum with `n` up to $10^{12}$. A loop over every `d` takes $10^{12}$ steps, far past the $10^8$ or so that a program can afford. The blocks cut it to about $2 \cdot 10^6$. The rest of this lesson shows why, and how to reuse the same blocks for memoization.

## Finding where a block ends

The loop has to know the last `d` whose quotient is still `q`. It is `n // q`. To see why, note that $n // d \ge q$ holds exactly when $d \le n / q$, so the largest `d` that still has a quotient of at least `q` is `n // q`. Quotients never rise as `d` grows, so at that `d` the quotient is exactly `q`. The next block then starts one past it.

Since the loop runs only while `d <= n`, the quotient `q` is at least 1, so `n // q` never divides by zero. A loop that ran past `n` would meet `q = 0` and need a guard.

## Why there are only about 2 sqrt(n) blocks

Split `d` at $\sqrt{n}$. There are at most $\sqrt{n}$ values of `d` up to it, so they give at most $\sqrt{n}$ quotients. Above it, `d` times `n // d` is at most `n`, so the quotient is below $\sqrt{n}$, and there are fewer than $\sqrt{n}$ such values. The total is at most about $2\sqrt{n}$. This needs `n` held fixed while `d` varies. For one fixed `d` and a changing `n`, no such saving exists.

## Memoizing over the blocks

Sometimes each term is not a number but a value that depends on `n // d`. Say `cost(v)` is `v` plus the sum of `cost(v // d)` for `d` from 2 to `v`, with `cost(1) = 1`. The facts that make this cheap are simple: `v // d` for `v = n // a` equals `n // (a * d)`, which is again a value of the form `n // something`. So every subproblem that appears is one of the roughly $2\sqrt{n}$ quotients of `n`, and the memoization of M4.11 needs a table of that size instead of one of size `n`.

The program finds those quotients with the block loop, sorts them smallest first, and fills `cost` in that order. Each entry sums its own blocks, so it only looks up entries already stored.

The dictionary is keyed by integers, and the loops are plain `while` loops with no recursion, which PyPy handles well. Filling from small values up also means no recursion limit is needed.

Reach for this when a sum or recurrence depends on `n // d` for every `d`, and `n` is too large to loop over. Count the distinct quotients first, then decide whether a plain block sum or a memo table over them fits.
