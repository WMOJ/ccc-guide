An ordinary shortest path from room 0 to some room does not answer this, because the robot has to remember which checkpoints it has already collected. Make that memory part of its position and the puzzle becomes a shortest-path search over a bigger graph. Keeping that bigger graph small is called <Term id="sparsification">sparsification</Term>.

## A state is what the future depends on

Two robots standing in room 1, one that has already been through room 2 and one that has not, face different problems. So a **state** is the smallest description that still decides what can happen next. Here it is a pair: the room, and the set of checkpoints collected so far. The state graph has one node per state, and an edge for each legal move from one state to another. The start is (room 0, nothing collected). A goal is any state with every checkpoint collected, in any room. Walking a corridor from room `u` to room `v` moves you from (`u`, collected) to (`v`, collected plus `v`, if `v` is a checkpoint), and costs the corridor's time.

Store the collected set as one integer, a mask. Checkpoint number `i` owns bit `i`, the value `1 << i`, and `mask | bit` switches a bit on while keeping every bit already on. Step through the short program below. It walks the route 0, 3, 0, 1, 2 through a five-room building and prints the mask after each room. Try the second preset too.

## How big is the full graph?

With `n` rooms and `k` checkpoints there are $n \cdot 2^k$ states. A contest map could have $n = 10^5$ rooms, $2 \cdot 10^5$ corridors and $k = 10$ checkpoints. That is $10^5 \cdot 1024 \approx 10^8$ states, and each corridor is an edge once per mask, about $4 \cdot 10^5 \cdot 1024 \approx 4 \cdot 10^8$ moves. Running Dijkstra over every state is the brute-force plan. PyPy does roughly $10^7$ to $10^8$ simple operations per second, and each move here can be a heap push, so that plan is out of reach.

## Search only what the start can reach

The first saving is not to build the graph at all. Dijkstra's algorithm from M6.1 needs only the edges leaving the state it just settled, and a way to know which states are done. Both can be computed on demand.

The loop is M6.1's with one extra field. A heap entry is `(distance, room, mask)`. Checkpoint rooms have a nonzero `bit`, and every other room has 0, so `mask | bit[v]` only changes the mask when the robot enters a checkpoint. The `best` and `done` lists are flat: the state (room `u`, `mask`) lives at index `u * size + mask`, which is row `u` and column `mask` of a table with one row per room and one column per set. A stale entry is skipped exactly as in M6.1. The search stops at the first settled state whose mask holds every checkpoint. As in M6.1, a settled distance is final, so the first goal state out is the nearest.

## Keep only the edges that matter

The second saving comes from asking which rooms the answer can depend on. Only the start and the checkpoints, the key rooms, are ever decision points. Every other room is somewhere the robot merely passes through on the way between two key rooms. So instead of moving one corridor at a time, move from one key room straight to another along its shortest route.

To build that smaller graph, run Dijkstra from each key room on the plain map, with no masks, and keep only the shortest distances between key rooms. Step through it below. The last step swaps the map for the graph you keep.

Why is the smaller graph enough? Take any route that collects every checkpoint and cut it at the moments it first enters each checkpoint. Each piece runs between two key rooms, so it is at least as long as the shortest distance between them. Replacing every piece by that shortest route cannot make the total longer, and every order of pieces is a genuine walk on the map. So the best order in the kept graph costs exactly what the best route on the full map costs.

`dijkstra` is M6.1's loop, run once per key room: `dist[i][room]` is the distance from key room `i`. A state is now (key room `i`, `mask`), and a move goes to checkpoint `j` at cost `dist[i][keys[j]]`. A move to a checkpoint already in the mask is never generated, because returning to a collected checkpoint can only add time. Write that test as `not (mask & bit)`: `&` ranks below `==` in Python, so `mask & bit == 0` would compare `bit` with 0 first.

## Confirm the smaller graph solves the problem

A shrunken graph is only useful if it gives the same answer. Both programs read the same map and print a distance of 7. The sizes differ: 4 of 12 states settled here, against 7 of 20 in the full search. Make that check on any sparsified graph. Keep the simple, obviously correct search, run both on small maps, and compare the answers before you trust the fast one.

On the large map the cost moves into the ordinary searches. Eleven runs of Dijkstra cost about $11 \cdot 3 \cdot 10^5 \cdot 17 \approx 6 \cdot 10^7$ steps, and the search over $11 \cdot 1024$ states adds only about $10^5$ moves, against about $4 \cdot 10^8$ for the full graph.

## Making it fast on PyPy

Both programs keep every per-state value in a flat list, one row per room and one column per mask. A dictionary keyed by a tuple, or a `frozenset` of collected checkpoints, would allocate and hash a new object for every state. An integer mask costs nothing to build, compares by value inside the heap, and needs no hashing. Read the whole input once with `sys.stdin.read().split()`, and never store the state graph's edges: build them from the map as the search settles each state.

Reach for state-space modeling whenever the answer depends on more than where you are: what you carry, which doors you have opened, how much fuel is left. Put that into the state and count the states. If the count is too large, ask which rooms and moves the answer cannot depend on, and keep only those.
