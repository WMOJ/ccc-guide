Four piles of stones sit in a row, with sizes 2, 3, 5 and 7. One move merges two neighboring piles into one, and the move costs the sum of the two sizes. You keep merging until one pile is left. What is the cheapest total?

Merge 2 and 3 for 5, merge that pile with the 5 for 10, then merge it with the 7 for 17. The total is 5 + 10 + 17 = 32. Other orders cost more, and the table below shows why: the final merge always joins everything and costs 17, so the orders differ only in what they pay before it.

The 32 in the first row is the answer we are after. Finding it without listing every order is a job for <Term id="interval-dp">interval DP</Term>: a <Term id="dynamic-programming">dynamic programming</Term> table whose entries describe contiguous intervals of the row.

## Why not try every order

The number of merge orders for `n` piles is the Catalan number for `n - 1`. That is 14 for five piles and about `1.8 * 10^9` for twenty. Contest inputs can have `n = 400`, which is more than `10^200` orders. Trying them all is out of the question, so we need a table with only polynomially many entries.

## The last merge splits the row

Look at the final merge of any order. It joins a left block, piles `i` through `k`, and a right block, piles `k + 1` through `j`. Let `dp[i][j]` be the cheapest way to merge piles `i` through `j` into one pile. Then:

`dp[i][j] = min over k of (dp[i][k] + dp[k + 1][j]) + (piles[i] + ... + piles[j])`

Why is this correct? Only neighbors merge, so once the last merge is fixed, the left block had to become one pile using only its own piles, and likewise the right block. Nothing in one block can affect the other. Each block should therefore use its own cheapest order, which is what `dp[i][k]` and `dp[k + 1][j]` hold. The last merge costs the whole range sum, whatever `k` is. Prefix sums from M4.3 give that sum in constant time.

## Fill the table from short intervals to long

`dp[i][j]` needs `dp[i][k]` and `dp[k + 1][j]`, and both are shorter intervals. So fill by length: every single pile first (`dp[i][i] = 0`, since nothing is merged), then every interval of length 2, then 3, and so on up to the whole row. This order guarantees every cell's two inputs are ready. A table filled row by row would ask for cells that are still empty.

## Counting the work

There are about `n^2 / 2` intervals, and each tries up to `n - 1` splits. Counting exactly, the innermost line runs `(n^3 - n) / 6` times: 84 for eight piles and 10,666,600 for `n = 400`. PyPy manages roughly `10^8` simple steps a second (M2.9), so that is comfortable. At `n = 5000` the same count is about `2 * 10^10` and no longer is.

The prefix sums matter here. Adding up the range inside the `k` loop would cost another factor of `n`, but with `pre` the range sum is two lookups, computed once per interval outside the `k` loop. Now watch the actual lines run on three piles. The trace skips over most of the prefix-sum loop.

## Knuth's optimization

When `n` grows past a few thousand, the `n^3` loop is too much, and some costs allow a faster table. Write `opt[i][j]` for the best split `k` of interval `i..j`. Knuth's optimization says: if the added cost `w(i, j)` satisfies the quadrangle inequality, `w(a, c) + w(b, d) <= w(a, d) + w(b, c)` for `a <= b <= c <= d`, and is monotone (an interval inside another never costs more), then

`opt[i][j-1] <= opt[i][j] <= opt[i+1][j]`.

Range sums of non-negative piles meet both conditions, so this problem qualifies. The proof of the statement is longer than this lesson, but you can test it: the example below gives the same answers as the plain loop. It tries only `k` from `opt[i][j-1]` to `opt[i+1][j]`, never past `j - 1`.

The output shows 49 splits tried against 84. On eight piles that is a small saving, but the window costs add up differently. For one interval length, the windows of neighboring intervals share endpoints, so their sizes telescope: the total over all intervals of that length is at most about `2n`. Over all `n` lengths that is `O(n^2)`, about 320,000 for `n = 400` against 10,666,600.

The conditions are the catch. If the cost does not satisfy them, the window can skip the true best split and the program prints a wrong answer with no warning. Check the conditions for your cost, and compare against the plain loop on small random inputs before trusting it.

## When to reach for it

Reach for interval DP when a row shrinks or combines from the inside out and the cost of a step depends on the interval it covers. Define `dp[i][j]` on intervals, try the last step's split `k`, and fill by length. Start with the plain `O(n^3)` form and count its work against the limit. Add Knuth's window only when that count is too large and the cost meets the conditions.
