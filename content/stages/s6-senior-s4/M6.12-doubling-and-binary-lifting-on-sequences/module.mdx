## Bounds, and why walking does not scale

Suppose a problem allows `n` and the number of queries `q` up to 200,000, with `K` up to 10^9 jumps per query. Walking makes up to `q * K` = 2·10^5 × 10^9 = 2·10^14 hops. The program above made 35 hops for three small queries, which is fine, but at this size it is far past the 10^8 or so simple operations a solution can afford (M2.9). Notice that the walk in the figure visits station 3 again on jump 8 and on jump 13, because the stations 3 to 7 form a loop. You could detect the loop and skip whole laps, but that trick depends on the shape of one graph. A table of jumps works for any `K` and, in M7.13, for climbing a tree toward its root.

## Jump in powers of two

<Term id="binary-lifting">Binary lifting</Term> answers any number of jumps by combining a few big jumps whose sizes are powers of two. Every `K` is a sum of distinct powers of two, its binary digits: 13 is `1101` in binary, so 13 = 8 + 4 + 1. If you already know where 1 jump, 4 jumps and 8 jumps from any station land, a 13-jump query is three lookups instead of thirteen hops.

The table is named `up`. Entry `up[k][v]` is the station you reach after `2^k` jumps from station `v`. Level 0 is the teleporter list itself, `up[0] = nxt`. Mind the meaning of `k` here: row `k` holds jumps of size `2^k`, not size `k`.

## Build each level from the one before

Level `k` needs no walking. To jump `2^k` from `v`, jump `2^(k-1)` to some station `m = up[k-1][v]`, then jump `2^(k-1)` again from `m`. Two halves of length `2^(k-1)` make a jump of `2^k`:

`up[k][v] = up[k-1][up[k-1][v]]`

## Answer a query from the set bits of K

To answer a query, start at the station and walk the bits of `K` from bit 0 upward. When bit `k` is set, replace the current station with `up[k][here]`. When it is clear, do nothing. For `K = 13` from station 0, the set bits are 0, 2 and 3. The three cells that matter are marked below.

A hop of 8 followed by a hop of 4 lands on the same station as 4 followed by 8, because both add up to 12 jumps. Going from the high bit down gives the same answers as going from the low bit up.

## Why it is correct, and what it costs

The table is right by induction. Level 0 is the teleporters. If `up[k-1][v]` is correct for every station, then `up[k][v]` jumps `2^(k-1)` to `m` and `2^(k-1)` more, and `2^(k-1) + 2^(k-1) = 2^k` jumps in total. A query is right because the binary form of `K` is unique and its powers add up to `K` exactly, so the hops total `K` jumps and nothing is skipped or counted twice.

With `n` = 2·10^5 and `K` up to 10^9, `LOG` = 30, so the table has 6·10^6 entries and building it takes about 6·10^6 lookups. The queries add `q * LOG` = 6·10^6 more. That is about 1.2·10^7 operations in total, against 2·10^14 for walking. If `K` could reach 10^18, `LOG` would be 60 and the work doubles, which is still small.

## Making it fast on PyPy

The table is a list of lists of plain integers, which PyPy stores compactly: 6·10^6 entries is on the order of 50 MB. Build each level with one list comprehension over the level before it, not a loop that rebuilds it entry by entry. Read all the input at once with `sys.stdin.read().split()` and write the answers with one `sys.stdout.write`.

## When to reach for it

Reach for a doubling table when every node has one next node and the structure does not change between queries. The signal is a query that asks where you are after a huge number of steps. The same table is the core of tree ancestor queries in M7.13, and a sparse table in M7.3 uses the same doubling idea on ranges of an array.
