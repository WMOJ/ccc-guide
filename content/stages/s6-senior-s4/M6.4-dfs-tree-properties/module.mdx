A build system has five tasks, and some tasks cannot start until others finish. If task 2 needs 1 and task 1 needs 3, but task 3 also needs 2, the build can never start. Two questions follow. Is there a circular dependency anywhere, and if not, in what order can the tasks run?

Both come from one depth-first search, as long as you record when it enters and leaves each node. Checking for a cycle by starting a separate search from every node costs about $n(n + m)$ steps. With $n = m = 2 \cdot 10^5$ that is $8 \cdot 10^{10}$. A single search costs $n + m$, about $4 \cdot 10^5$, and its entry and exit times answer both questions.

## Discovery and finish times

Keep a clock that starts at 0 and ticks each time the search enters a node and each time it leaves one. A node's discovery time is the clock when it is entered. Its finish time is the clock when every edge out of it has been tried and the search leaves it. Each node then has an interval from discovery to finish.

## Four kinds of edge

The search follows edges, and each edge, the first time it is tried, leads to a node in one of four situations. A <Term id="tree-edge">tree edge</Term> leads to a node with no discovery time, so the search enters it. A <Term id="back-edge">back edge</Term> leads to a node that is discovered but not finished: it is on the stack, an ancestor of the current node. A <Term id="forward-edge">forward edge</Term> leads to a finished node that was discovered after the current one, a descendant reached by another route. A <Term id="cross-edge">cross edge</Term> leads to a finished node that was discovered before the current one, in a branch that closed earlier.

## Why the times give the kinds

The stack makes every pair of intervals either nested or disjoint, never partly overlapping. If node `v` is entered while `u` is still on the stack, `v` leaves first, so `v`'s interval is inside `u`'s. Otherwise `v` is entered after `u` has left, and the intervals do not touch. So an edge from `u` to `v` has a kind you can read off the two intervals.

In the table, tree and forward edges end inside the interval they start in. A back edge ends at an interval that contains the start. A cross edge ends at an interval that closed before the start opened. The same reading also tests ancestry: `a` is an ancestor of `b` exactly when `b`'s interval lies inside `a`'s.

## Cycles

A directed graph has a cycle exactly when its search finds a back edge. A back edge from `u` to an ancestor `v` closes a loop with the tree path from `v` down to `u`. In the other direction, take a cycle and its first-discovered node `c`. Every other node on the cycle is reached from `c` before `c` finishes, so the edge that comes back into `c` meets a node still on the stack, which is a back edge.

## Topological order

If the graph has no cycle, a valid task order is the nodes listed by decreasing finish time. Take any edge `u → v`. It cannot be a back edge, so it is a tree, forward or cross edge. In each case `v` finishes before `u`: inside `u`'s interval for tree and forward edges, and entirely before it for a cross edge. So `u` comes first when the finish order is reversed.

## Undirected graphs and PyPy

An undirected graph stores each edge in both directions. Only tree and back edges can appear, and the edge back to the parent you just came from is not a cycle, so skip it once. The number of trees is then the number of connected components.

Keep `disc` and `fin` as flat lists and the stack as a list of two-item lists, and build the output lines first and print them once. Nothing recurses, so a chain of $2 \cdot 10^5$ nodes cannot hit the recursion limit, and each edge is handled once.

Reach for these times when a problem asks for a cycle in a directed graph, or an order that respects dependencies. They also tell you whether one node sits under another in a search tree.
